## Installed library and production path

Reviewed local `websockets`16.1.1, specifically `asyncio.connection.Connection.keepalive`, `ping`, `acknowledge_pings`, `data_received`, `process_event`, `connection_made`, and `asyncio.messages.Assembler`. Local source/version hash is saved in ignored `data/early_edge/ping-timeout-20261025/initial.json`. The WSL receipts do not independently pin the installed WSL library build; local mechanism tests are not proof of a byte-identical WSL installation.

In [OnchainPumpDiscovery.run](../app/discovery.py), one standard confirmed `logsSubscribe` is read sequentially. `await wait_for(ws.recv(),90)` is followed by synchronous JSON parsing and `receive(payload)`. `receive` validates/scopes invocation logs, decodes canonical events, invokes synchronous bounded recovery scheduling/gap callbacks and `RadarEngine.submit`. Submission uses the bounded priority queue; it does not await HTTP or durable persistence. Other engine tasks share the event loop: event processing, analysis, intelligence refresh and checkpoints may perform synchronous work. Thus client starvation is architecturally possible; it is not demonstrated as the cause here.

Installed keepalive sleeps for `ping_interval - previous_latency`, sends a ping through `send_context`, then awaits its matching pong future inside a20s timeout. On expiration it calls protocol.fail with local1011 and the fixed keepalive marker. `Connection.process_event` acknowledges pong frames directly in the protocol callback, independent of application `recv`. Application traffic alone does not acknowledge a ping. Timer callbacks and packet callbacks require event-loop service; scheduling and close-handshake time mean a recorded failure need not occur at exactly40s after ACK.

`connection_made` wires assembler high-water16/low-water4 to transport pause/resume reads. More than16 queued data frames pauses transport reads until the queue drains to4 or fewer. A later pong on that TCP stream may then be unread, even though keepalive is waiting. A pong already parsed in the same `data_received` callback is still processed: a full data queue does not itself discard pong frames. TLS/OS/network buffers and frame fragmentation further prevent mapping application message counts to frame-buffer occupancy. `max_queue` is a high-water mark, not an absolute frame-memory ceiling for a single incoming chunk.
